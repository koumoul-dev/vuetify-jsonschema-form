# V2 compatibility

`@koumoul/vjsf/compat/v2` exports a `v2compat()` function that takes a
VJSF-2 schema (with its `x-display`, `x-fromData`, `x-fromUrl`, etc.
annotations) and returns a schema using the VJSF v3+ vocabulary:

```js
import { v2compat } from '@koumoul/vjsf/compat/v2'
const v3Schema = v2compat(schema)
```

It translates the vast majority of the v2 annotations vocabulary
(properties layout, selects, sections, arrays, dynamic content, etc.) so
that most v2 schemas keep working with little to no change. It is **not
100% compatible**: some patterns have no v3 equivalent (for example the
`eval-expr` syntax used in a few `x-fromData` expressions, or the
`rootDisplay` option). Always test your own schemas after conversion
rather than assuming a 1-to-1 result.

The pages in this section reuse the example library from the old VJSF v2
documentation, each schema passed through `v2compat()` and rendered live,
so you can compare what a v2 schema produces once converted:

- [Properties & selects](/migration/v2-compat-properties)
- [Sections & arrays](/migration/v2-compat-sections-arrays)
- [Dynamic & advanced](/migration/v2-compat-advanced)

## Using v2compat as a migration aid

If you are migrating an existing v2 application, run your schemas through
`v2compat()` at the start of the migration, get the app working again with
minimal changes, then progressively rewrite each schema to the native v3+
vocabulary at your own pace (the new vocabulary is more expressive and
better documented, see [components](/components) and
[behavior](/behavior)).

## Using v2compat permanently

`v2compat()` can also be used indefinitely, at runtime or at build time
alongside [schema compilation](/behavior/compilation), if you would rather
keep your schemas written in the v2 vocabulary (for example because they
are generated by other tooling you do not control). There is a small
runtime/build cost to the conversion step itself, but the resulting form
behaves the same as a native v3+ schema.
